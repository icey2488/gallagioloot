# GallagioLoot Proxy — Project Instructions for Claude Code

Data layer + decision engine for GallagioLoot (WoW bonus roll optimizer): a Cloudflare Worker that fetches Raidbots droptimizer reports and QE Live upgrade reports and normalizes both into a shared `NormalizedReport` schema, plus a pure `src/core/` module (no Worker/runtime dependencies) that turns a normalized report and a knockout state into a bonus-roll recommendation. The static site UI lives in `web/` (a second Worker, see Design below).

## Code style

- **TypeScript, with a build-free Workers runtime.** Wrangler bundles `src/index.ts` directly; no separate build step to run locally.
- Keep normalizer logic (`src/normalize/raidbots.ts`, `src/normalize/qelive.ts`), the encounter-items lookup (`src/lookup/encounterItems.ts`), and the decision engine (`src/core/`) **pure** — no `fetch`, no Cache API/KV access, no `Date.now()` (timestamps are caller-supplied) — so they're testable with plain fixtures and importable by a future frontend. `src/index.ts` (the Worker handler) does all I/O and calls into these.
- Minimal dependencies: standard library + Workers runtime API + `@cloudflare/workers-types` only.

## Testing

- `npm test` runs the fixture-based unit tests (`test/*.test.ts`, vitest). These must stay hermetic — no real network calls.
- `npm run test:live` runs `test/integration.test.ts` against the real Raidbots/QE Live APIs. Skipped by default (gated on `RUN_LIVE=1`); don't let it run in CI.
- `npm run typecheck` runs `tsc --noEmit`. CI runs typecheck + unit tests on every push (`.github/workflows/ci.yml`).
- Don't merge a normalizer or lookup change without unit test coverage for it.

## Deployment

- Not deployed automatically; nothing deploys from git (DEPLOY.md). The root `wrangler.toml` route for `gallagioloot-proxy.icehunter.net` is active (`custom_domain = true`), as is `web/wrangler.toml`'s for `gallagioloot.icehunter.net`. Don't deploy without explicit instruction.

## Design (web/)

Hard rules for the `web/` UI (Cloudflare Worker static site, see `web/CLAUDE.md`-equivalent context below -- there's no separate file, this is the canonical copy):

- No gradients, glow, or neon effects.
- WCAG AA contrast (verified with `web/design/contrast.mts`).
- Tabular figures for numbers (`font-variant-numeric: tabular-nums`).
- Disclaimers live in the in-flow footer, not a modal/overlay.
- No external assets (fonts/icons are bundled, not fetched from a CDN at runtime; IBM Plex Sans is self-hosted through the `@fontsource/ibm-plex-sans` package, so there is no Google Fonts link).
- Gold accent rule (superseded 2026-09-20; previously "exactly one gold accent per screen, card only"): The recommendation card carries the strongest gold treatment on any screen (border + headline + primary action); everywhere else gold is accent-weight only: wordmark, active-tab underline, Voidcores pill glyph/number, section expander "+" marks, selected-row stripe, primary buttons, small heading bars. Never gold on body text, table numbers, or large fills.

## Behavior

- Endpoints: `GET /raidbots/:id`, `GET /qelive/:id`, `GET /encounter-items` (debug), `GET /tier-map/:instanceId` (debug), `GET /loot-table/:instanceId?lootSpec=:specId`, `GET /health` (reports the current Raidbots static-data hash + its age). See `README.md` for the full schema and upstream shape notes, including mismatches found against the original spec (the Raidbots data-hash discovery location, `encounter-names.json`/`instance-names.json` being flat objects rather than arrays, and the Tidebound Grotto instance/encounter id in the tier seed table — see "Tier-token resolution" in README.md).
- `getEncounterItemsLookup` re-discovers the Raidbots static-data hash automatically if the cached one starts 404ing (the hash rotates periodically) — see `src/lookup/encounterItems.ts` and its regression test.
- Loot-spec eligibility (`src/lookup/lootEligibility.ts`, `src/lookup/lootTable.ts`) and the static spec table (`src/lookup/specs.ts`) back the `/loot-table` endpoint and `PoolEntry.specSpecific` in `src/core/`. See README.md's "Loot specs" and the `/loot-table` endpoint section for the eligibility rules and one open uncertainty (shield/off-hand item restrictions, and the invented "Devourer" Demon Hunter spec's role).
- Loot eligibility also filters on **primary stat** (`stats[]` ids 3/4/5, multi-primary 71-74 vs `SpecEntry.primaryStat`): `weapon-specs.json` is equip-based, so without it a Strength sword or Agility dagger showed up in a Mage's pool (Jaw of the Shackled Goddess, Zatha'tek). Ula'tek's Arcane pool is pinned to the journal's 4 items in `test/lootTable.primaryStat.test.ts`.
- Tier-set armor items (head/shoulder/chest/hands/legs tokens) aren't joinable via `encounter-items.json` alone (Raidbots points them at an aggregate catalyst bucket). `src/lookup/tierSeed.ts` (static, hand-maintained) and `src/lookup/tierLearned.ts` (persistent cache learned from Raidbots reports) resolve them instead; see README.md for the full design and detection method.
- Mythic+ droptimizers (aggregate instance -1, every row `-1/-1/...`) are attributed to dungeons via the itemLibrary sources join; each dungeon is a repeatable `mplus` target. Several reports (raid difficulties + one M+) can be ranked together (`src/core/targets.ts`, `src/core/reportSet.ts`); catalyst rows credit their source item at max(own, catalyzed). See README.md "Raidbots Mythic+ droptimizer" and "Decision engine".
- **Curio is not a bonus-roll outcome** (Erick's Adventure Journal ruling, 2026-09-24; supersedes the earlier "Curio is one pool entry" rule): Ula'tek's Slumbering Coil Curio (tier seed 2895, `viaCurio` rows) can't be won with a bonus roll, so it is never a `PoolEntry` -- not in the pool, the denominator, best case, rolls-to-target or knockout (`src/core/pool.ts`, `src/core/curio.ts`). Catalyst credit for real items is unchanged. The web UI hides the curio row and notes why under Ula'tek's table; stored knockout entries that reference it are ignored on load and dropped on save.
- **Equipped gear is auto-Owned only when it isn't a sim upgrade** (v2.06, corrected v2.07): Raidbots reports carry the sim profile's equipped gear (`rawFormData.droptimizer.equipped`); `NormalizedReport.equippedItemIds` holds its item ids (`src/normalize/equipped.ts`; QE Live's payload has none). `buildBossPools` marks a pool entry whose itemId is equipped `PoolEntry.equipped`, and treats it as Owned (a value-0 dud, `autoOwned`) unless the knockout state has an entry of its own **or the sim shows an upgrade** (best delta incl. catalyst credit > 0; the drop copy is then a higher item level than the worn one). Upgrades keep their value, default to None and set `equippedUpgrade`; the web UI labels them "Equipped (lower ilvl)" and offers None / Owned / Rolled, while auto-Owned rows say "Equipped" and offer Owned / Rolled. The sim delta is the source of truth (no ilvl comparison). The default is never stored. Matches by itemId alone (no ring/trinket unique-equip reasoning).
- **Per-report drops and the Reports panel (v2.08)**: each report shows as one compact block (`web/src/components/ReportBlock.tsx`): heading + Remove, a drop line (`Drops Myth 6/6 (334) · The Coiled Altar, Ula'tek Myth 9/6 (344)`, from `summarizeDrops`/`formatDropLine` in `src/core/drops.ts`, read off the report's own rows and item labels, never hardcoded per boss), then items / bosses / baseline / sim date (`NormalizedReport.simmedAt` = Raidbots `data.json` `Last-Modified`, QE Live `timeCreated`). Warnings collapse under an "N notes" toggle, open by default only for an error. A once-per-panel strip shows "Voidcores on hand" (the Voidcores-held setting) and, since v2.09, "One more Voidcore: ~X%" (`planVoidcores(...).extra` in `src/core/supply.ts`). The 344 rows carry only `overrides.itemLevel: "Myth 9"` (no `upgrade` object); `parseTrackInfo` treats that as a step past max ("Myth 9/6"), never a max-upgrade warning.
- **Voidcore supply (v2.09, operator rulings 2026-09-25; supersede "Rolls available 1/2")**: earning is at most 1 Voidcore a week from the Great Vault plus 1 more a week from season week 8 (another source); Voidcores are held until season end (unspent = lost); there is **no weekly spend cap** (limits: Voidcores held + targeting rules). `src/core/supply.ts` `planVoidcores` orders the Voidcores to spend this week (Run settings: on hand, to spend (default = on hand), earned per week (default 1, 2 once next week is season week 8, i.e. from season week 7), optional season week / weeks left), flags below-threshold rolls, compares each with its hold value next week and shows what waiting costs ("playing without ~X% for 1 week", `holdCostText`; v2.10 operator ruling, no NPV or discounting) (after next week's earned + carried Voidcores take the top targets), warns on a season-end stockpile, and values one more Voidcore (the vault's Voidcore side in `compareVault`). `Settings.voidcoresToSpend` replaced `rollsAvailable`; the web migrates a stored `rollsAvailable: 2` to 2 earned per week. The eight supply assumptions (`VOIDCORE_ASSUMPTIONS`, v2.10 added the plain "Holding delays the upgrade" line) are listed in the footer. The card's "Next best" line says "the pick holds" only when `recommendation.tossUp` is null (one toss-up determination for the boss-vs-boss comparison).
- **Plan disclosure (v2.11, operator rulings 2026-09-25)**: no keys-per-week input. Whenever the roll plan uses a Mythic+ dungeon, the card (under the roll order) and the "One more Voidcore" strip state the assumption, e.g. "Plan assumes you run Murder Row at +10 twice this week." (`mplusAssumptionText`, `extraMplusAssumptionText`, `runCountPhrase` in `src/core/supply.ts`; count = rolls the plan assigns to that dungeon); a plan with no dungeon says nothing about Mythic+. The stockpile check treats a deployable dungeon as unlimited rolls, so its warning never counts M+ runs and carries no M+ assumption. Under the roll order (any plan with at least one roll, raid or M+) the card shows `ROLL_ORDER_REMINDER` ("This order holds until your next roll result. After a win ... re-run your droptimizer and GallagioLoot ..."); the footer has the same idea as the ninth supply assumption.
- **Themes (v2.12, operator rulings 2026-09-25)**: color tokens only; layout, spacing, fonts and components never change per theme. Midnight is the `:root` default in `web/src/theme.css` and adopts the Claude Design export's brighter gold (`--gold #e3b94a`, `--gold-strong #f0c75a`, `--gold-text-on #0b1426`, `--bg-hover #1a2748`; the old values sit in a comment there so reverting is one edit). Felt green and Craps red are `:root[data-theme='green'|'red']` token sets (values from the export's THEMES table, pinned by `web/test/theme.test.tsx`). The picker (`web/src/components/ThemePicker.tsx`, header, accessible name "Theme") persists to `localStorage` `gallagioloot:theme` (`web/src/lib/theme.ts`); `web/index.html` applies it before first paint. No hardcoded colors outside the token blocks (the warning/badge status colors are `--warn-*`/`--ok-*` tokens; a test enforces it). `web/design/contrast.mts` reads the palettes from `theme.css` and audits every theme; the gold one-accent semantics are the same in all three.
- **Multiple report URL rows (v2.13)**: the Reports panel takes 1-8 report URL rows (`web/src/components/ReportUrlRows.tsx`, pure logic in `web/src/lib/reportRows.ts`, URL normalizer `web/src/lib/reportUrl.ts`). "+" adds a row (disabled at 8 with a "Max 8 reports" hint); with 2+ rows each has a "-" (single row: none); removing a row never removes a loaded report. The button reads "Fetch all" when 2+ rows have URLs (otherwise "Fetch report", or "Add report" once something is loaded); it fetches every filled row in parallel, then adds the results in row order so each is checked against the set the earlier rows built (same character + loot spec, drift, one M+ droptimizer). Each row shows its own status (Fetching… / Loaded <title> / the error or refusal); a bad URL fails alone, and a loaded row clears its input. Duplicates are blocking errors, compared by normalized `<source>:<report id>` (host case, trailing slash, query and fragment ignored): the later row reads "Duplicate of row N", a report already in the panel reads "Already loaded"; both show when the user leaves the field or clicks Fetch and the row is not fetched (the message is frozen at click time). Top Gear stays a separate field. Color tokens only; `design/contrast.mts` audits the new pairs in all three themes; `design/reportRowsChecks.mts` is the shared browser suite (local fixtures in `single-page-shots.mts`, real proxy in `check:live`).
- **Version stamp, source and license links (v2.14, License added v2.15)**: the existing footer ends with "v2.15 · <short sha> · Source · License" (`web/src/components/Footer.tsx`, `.app-footer__stamp`). The version is the `APP_VERSION` constant in `web/src/lib/buildInfo.ts` (the single source of truth; bump it per spec version -- `web/package.json` stays 0.1.0). The sha is injected at build time by `web/vite.config.ts` `define` (`__BUILD_SHA__`, `__BUILD_FULL_SHA__`, `__BUILD_DIRTY__`, read by `web/build-info.ts` from `git rev-parse` / `git status --porcelain`), never hand-typed; a dirty tree appends "-dirty" to the shown sha (the link still names the clean commit), and a build outside a git checkout shows "v2.15 · Source · License" only. The sha links to `https://github.com/icey2488/gallagioloot/commit/<full sha>`, "Source" to `https://github.com/icey2488/gallagioloot`, "License" to `https://github.com/icey2488/gallagioloot/blob/main/LICENSE` (accessible name "License on GitHub (opens in a new tab)"); all open in a new tab (`rel="noopener noreferrer"`) with accessible names ("Commit <sha> on GitHub (opens in a new tab)"). `buildFooterStamp` (label/URL builder) is pure. Deploy from a clean tree at the final pushed commit so the stamp equals origin/main (DEPLOY.md). Color tokens only; `design/contrast.mts` audits the four stamp pairs in all three themes (the License link reuses the stamp-link pair); `design/footerStampChecks.mts` is the shared browser suite (`single-page-shots.mts` against the local build, `check:live` against the deployed site: sha must equal `git rev-parse --short HEAD`, no -dirty).
